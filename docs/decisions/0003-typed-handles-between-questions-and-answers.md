# 0003 Typed handles between questions and answers

## Context and problem statement

The TypeSafe API takes a map of question ids to questions and returns a map of the same ids to answers. Nothing on the wire connects a Noul question to a Noul answer, and a Choice answer's option is a string. How should the Rust client expose answers so that consumers cannot misread them?

## Decision drivers

- A misread number in a paging decision is worse than a failed request
- Request criteria and answer parsing must not drift apart
- Runtime option sets (incident references, catalog groups) must remain possible
- The client should stay small enough to read in one sitting

## Considered options

1. Typed handles: adding a question returns `Handle<A>`; `Response::get(&handle)` performs a checked conversion; closed option sets are enums generated by a macro
2. Raw maps: return the parsed JSON and let each consumer check the primitive and parse strings
3. A fully typed request struct per use case, with serde deriving both the request and the response shape

## Decision outcome

Chosen option: "Typed handles". `Questions::noul`, `choice`, `score` and `dynamic_choice` return `Handle<A>`. `Response::get` checks the primitive and converts. Closed option sets are enums implementing `Options`, generated by the `options!` macro, which also produces the request criteria.

### Consequences

- Good, because the request and the parser derive from one definition and cannot disagree
- Good, because a primitive mismatch or unknown option is an explicit error naming the question
- Good, because runtime option sets use `dynamic_choice`, and the boundary is visible in the type (`Choice<String>`)
- Bad, because there is more ceremony than a raw JSON call; the saving is paid back by every consumer

### Confirmation

`src/answer.rs` tests cover mismatch, unknown option, missing answer and out-of-range probabilities. `Probability` and `Confidence` are distinct validated newtypes.

## Pros and cons of the options

### Typed handles

- Good, because errors surface at the one place strings become types
- Good, because handles are cheap markers; nothing extra crosses the wire
- Bad, because `dynamic_choice` consumers still map string keys back to their own data

### Raw maps

- Good, because it is the smallest possible client
- Bad, because every consumer re-checks primitives and re-parses strings, and a typo is found at runtime if at all

### Typed request struct per use case

- Good, because serde does the work
- Bad, because the API's map shape does not fit a struct per use case without a custom (de)serializer per struct, and speculative questions make the shape vary per request
