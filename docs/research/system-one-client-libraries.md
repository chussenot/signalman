# System One client libraries

The `judgment` crate was designed in one repository against one consumer. Between 2026-09-16 and 2026-09-25 about twenty-five other Rust crates for the same wire appeared on crates.io, TypeSafe's Python SDK reached 0.7.1, and a live OpenAPI document turned out to exist. Before spending more on the crate it is worth knowing what the field converged on, where judgment is ahead, and where it is behind. This page is that survey: every crate's source was read, not its README, and every claim about the official API was checked against the SDK reference or the OpenAPI document on 2026-09-25.

The headline: the crate's architecture is confirmed, not contradicted. Three independent authors arrived at the same shape as judgment, typed keys that fix an answer's type, a backend trait with a fake behind it, and record-and-replay keyed by request content. What the field has that judgment lacks is wire hardening and parity with the official SDK: a request id on responses and errors, tolerance for answer kinds that do not exist yet, a contract test against the published schema, and the retry details the SDK documents. None of that is a reorientation. It is a 0.2, and it shipped as judgment 0.2.0 on 2026-09-25: [What shipped in judgment 0.2.0](#what-shipped-in-judgment-020) says how each ranked item landed.

Sources: the crates listed below, downloaded from crates.io; [the Python SDK reference](https://docs.typesafe.ai/sdk/python/api.md) and [usage guide](https://docs.typesafe.ai/sdk/python/usage.md), [the JavaScript SDK reference](https://docs.typesafe.ai/sdk/javascript/api.md), [the HTTP API page](https://docs.typesafe.ai/api.md); and `https://api.typesafe.ai/openapi.json`, version 0.2.0. [Open System One models](open-system-one-models.md) covers the models; this page covers only the clients.

## The field

None of the Rust crates is official. TypeSafe's [SDK page](https://docs.typesafe.ai/sdk.md) lists Python and JavaScript only. One crate, `typesafe-io`, declares the official organisation's repository and a documentation page as its home; the crate is owned by an individual account, the documentation page does not exist, and the crate has no retries and no user agent. Treat the claim as false.

The crates fall into five groups. Sizes are lines of Rust including tests; downloads are crates.io totals on 2026-09-25.

| Crate | Lines (approx.) | Downloads | What it is | The one idea worth knowing |
|---|---|---|---|---|

Eleven more (`jev-sdk`, `typesafe-systemone`, `jevlin`, `typesafeai-sdk`, `typesafe-sdk`, `typesafe-rust-sdk`, `typesafe-ai-client`, `typesafe-api`, `sysone`, `gaise-provider-typesafe`, `a3s-apofasi`) are thin ports or wrappers whose one idea, where there is one, appears in the rankings below.

Two facts about the population as a whole. Every crate that took the job seriously converged on the same three things judgment has: a typed key or handle that fixes the answer type (`typesafe-client`, `kunobi-jev`, `jevlin`), a trait over the wire with a scripted fake behind it (`typesafe-client`, `kunobi-jev`, `typesafe-rs`, `system-one`, `typesafe-jev`), and replay keyed by a hash of the request (`typesafe-ai-sdk`, `system-one`). Nobody has what judgment has in its `Observer` seam, its validated `Probability` and `Confidence` newtypes that refuse a bad value on deserialisation, its evaluation module wired to recordings, or a benchmark replay against a second implementation of the wire. Those are the parts to keep.

## What the official sources say that the crate does not know

This section and the ranking below describe judgment 0.1.0, the crate as it was surveyed; "the crate" means that release. What 0.2.0 changed is in [its own section](#what-shipped-in-judgment-020).

The OpenAPI document at `api.typesafe.ai/openapi.json` is version 0.2.0, describes `POST /v1/systemone` and `GET /v1/models`, and is identical to the copy `typesafe-client` vendored on 2026-09-16. It settles several things the crate's rustdoc guesses at:

- `GET /v1/models` is documented, with `ModelMetadata{name, description, release_date}`. The crate's note that the endpoint is "observed rather than documented" is wrong for the OpenAPI document, though the HTTP API page still omits it.
- A Score level is a string, an object or an array, never null; the legend maps a level number to that same value. The fix made in [the Laya run](../judgment-laya-typed-decisions.md) is what the schema says. A Choice description may be null.
- `instructions` is optional on every question type; the crate requires it. Score `criteria` has `minItems: 1`; the crate requires two, as the guidance recommends.
- A 422 body is FastAPI's `{"detail": [{"loc", "msg", "type"}]}`. The crate keeps the body as text; it could name the field.
- Nothing about 429, 529, `Retry-After` or a request id header is in the schema. Those are SDK behaviour, documented in the SDK reference and observed by every port.

The Python SDK reference, 0.7.1, fixes the client behaviour the crate claims to mirror:

- **Request id.** Every response and every API error carries `x-typesafe-request-id`. The exception carries status, body, headers, the endpoint without credentials and that id. The crate carries none of them, which is the first thing a support ticket asks for.
- **Retry budget.** The policy has a `timeout` of 30 s per call, "including the initial attempt and delays", and "stops before a retry whose delay would reach or exceed the budget". Jitter is subtracted, never added. `Retry-After` and `retry-after-ms` are both honoured. The crate has no budget, symmetric jitter and reads delay-seconds only; its rustdoc documents each as a deviation, so the claim of SDK parity is a half-truth that should become either parity or a stated policy.
- **Tolerance.** An answer whose `type` the SDK does not know is logged and skipped; `usage` fields are optional, "None when the API did not report it"; unknown fields are ignored. The crate, as of 0.1, fails the whole response on an unknown answer kind and requires `usage`. Every non-TypeSafe server in the survey exercised at least one of those: jigor returns no `usage`, zev adds answer fields, Laya adds three.
- **Escape hatches.** Per-call `model`, `retry`, `timeout`, `extra_headers` and `extra_body` (shallow-merged, for fields such as `beam_width`), and `response_model` for a typed struct of answers. The crate has none of the per-call overrides and no way to send a field it does not know.
- **Key hygiene.** The key is trimmed; an empty key, one with internal whitespace, control or non-ASCII characters is rejected before any request; an explicit empty key does not fall back to the environment. The crate filters blank keys and reports a bad one as a URL error.
- **Gateways.** OpenRouter (`https://openrouter.ai/api`, model `~typesafe/jev-latest`) and Vercel's AI gateway (`https://ai-gateway.vercel.sh/typesafe`, model `typesafe-ai/jev`) are documented `base_url` targets. `fuzzy-jev` shows OpenRouter's response adds `id`, `provider` and `usage.cost`, so the tolerance above is what makes a gateway work.
- **Confidence.** The reference gives the Choice confidence formula as approximately `(n·pmax − 1)/(n − 1)`, marked as a demonstration, and says a Noul has none. Useful for a `Fake` that wants realistic confidences; not a contract.

## Ranked: what to change in judgment

Each item names where the idea was seen, why it matters to this project, and the cost. The order is value per line of code.

1. **Carry the request id.** `x-typesafe-request-id` on `Response`, on `Error::Http`, `RateLimited`, `Overloaded`, `InvalidRequest` and `Unauthorized`, and as a field on the client span. Seen in the official SDK and six crates. Cost: one header read in the retry loop, one field on the completed-response type. Do it first.
2. **Decode tolerantly, validate strictly.** An unknown answer `type` becomes `Answer::Unknown(Value)` with a warning rather than a failed response, the known variants stay strict (kunobi's custom `Deserialize` is the pattern); `usage` and its fields default to zero when absent; unknown top-level fields are kept in a map so an operator can log Laya's `routing` or OpenRouter's `provider`. Seen in the SDK, kunobi, typesafe-rs, fuzzy-jev. Cost: small in code, but not additive: `Answer` was an exhaustive public enum, and under [Cargo's SemVer rules](https://doc.rust-lang.org/cargo/reference/semver.html#enum-variant-new) a new variant on one is a major change, since a consumer's exhaustive `match` stops compiling. The same release should make the enum `#[non_exhaustive]` so the next kind is not.
3. **Verify the response against the questions before returning it.** Every question id answered, every answer of the kind its question asked, every Choice key one of the options sent, every Score legend the levels sent. `typesafe-client` does this in the transport; judgment checks per handle, late, and only for the handles the caller reads. The same check makes `Fake` refuse a scripted answer that does not fit its question, which kunobi's fake does and which catches stale tests. Cost: one pass over the response, about sixty lines, and `Error::AnswerTypeMismatch` gains a sibling for an option outside the question.
4. **Test against the OpenAPI document.** Vendor `openapi.json`, validate every request the builders produce and every response the `Fake` and the committed recordings hold against its schemas with a JSON Schema crate in dev-dependencies, and add an ignored live test that the vendored copy still matches the URL. This is exactly what signalman does for incident.io and what `typesafe-client` does for this wire. Cost: one dev-dependency, one test file, a copied JSON file.
5. **Retry parity, stated.** Add `retry-after-ms` and HTTP-date `Retry-After` under the existing cap, make jitter one-sided, and add an optional total budget that skips a retry that cannot fit, off by default so no consumer's timing changes. Then the rustdoc can say which of the SDK's behaviours the crate matches and which it declines, rather than "mirrors" with footnotes. `typesafe-rs`'s `conservative()` preset, which does not retry 5xx because a retried POST is billed twice, is worth offering as a named policy for callers who prefer a failed triage to a doubled bill. Cost: medium, all in `http.rs`.
6. **Per-call overrides and an extra body.** `model`, `timeout` and `retry` per request, and a flattened map of extra fields on `Request`, plus extra headers on the builder. The official SDK has all of them; jev-rs's `debug` block and zev's `temperature` are what a consumer would put there. Cost: small; `Request` grows three optional fields.
7. **Fix the small things the schema shows.** `instructions` optional; 400 classified as `InvalidRequest` alongside 422 and 403 as its own variant, since jev-bridge returns 400 for a bad body; a dedicated `Error::InvalidApiKey` with the SDK's hygiene rules; parse the 422 `detail` list into field paths; correct the `/v1/models` note. Cost: trivial each.
8. **Distribution helpers as pure functions.** `ranked()`, `margin()` between the top two, `top(n)` on a Choice; `probability_at_least(level)` on a Score; the probability of the reported answer as a method rather than a lookup. Seen in kunobi, typesafeai-sdk-community, typesafe-rust-sdk, jev. They are pure, they cost nothing, and signalman's policy and the benchmark example re-derive them by hand. jev-bridge's finding that order flips cluster where the top-two margin is at or below 0.24 is the kind of rule a policy wants `margin()` for. Cost: trivial. What stays out: a `decide(min_confidence)` that returns an option, a three-band verdict, a cost-matrix decision. Those are policy, and decisions 0002 and 0008 keep policy in the application.
9. **Expose backend limits as data.** Maximum options, maximum levels and a context budget on the backend, so a caller can shortlist before the wire and the harness can report a refusal as a gap. Every small model in the [research note](open-system-one-models.md) caps options at 16 to 26; jev-bridge at 16; zev serves `/v1/limits`. Cost: a `Limits` value with a default for TypeSafe's 255 and 10, a method on the trait with a default implementation.
10. **A `Shadow` backend.** Send each request to two backends, return the first, record both. `system-one` has it; the Jev-versus-Laya comparison the roadmap wants is exactly this, and the evaluation harness would get paired requests for free. Cost: about eighty lines on top of `Recorder`.
11. **Order-flip rate in `eval`.** Rotate or reverse the option order and count changed answers; jev-rs averages rotations, jev-bridge measures the flip rate and found a real position bias on the reference endpoint. A `Replay` cannot do this, only a live run can, so it belongs beside the live tests. Cost: medium.
12. **Concurrency control.** A semaphore on the client (kunobi) or an AIMD pacer that halves on 429 (typesafe-jev, the community batch runner). signalman answers one alert per webhook today; the day it replays history in bulk or serves a burst, this is the first thing it needs. Cost: small for the semaphore, medium for the pacer. Wait for the need.

## Rejected, and why

- **Ten crates for one client** (the douglance workspace). The split buys nothing at three thousand lines and costs a release dance for every change. judgment's feature flag already separates the questions from the transport.
- **A cache of probabilistic answers** keyed by request (community SDK). A cached judgment is a stale judgment with a fresh timestamp; `Replay` exists for the one legitimate use, tests, and says so in its name.
- **Policy in the wire crate**: cost-matrix `decide`, entropy-based gates, sampling from the distribution (`system-one`, `jev`). Decision 0002 puts thresholds in code the application owns and tunes; a helper that hides the threshold moves it into a dependency.
- **A synchronous client.** Five crates ship one; no consumer here has asked, and blocking on the future costs one line.
- **Untagged, dual-dialect answer parsing** (`jev`), which accepts answers without a `type`. Item 2 keeps unknown kinds without loosening the known ones; a server that omits `type` (jigor guesses the kind from the fields) is outside the schema and should be fixed there.
- **Cassette compatibility with `typesafe-ai-sdk`**, whose key is the SHA-256 of the exact request body. judgment's key is a 64-bit hash of the canonical, key-sorted JSON, so two clients that serialise questions in a different order share a recording. The formats are documented on both sides; converting is a script, not a feature.
- **Reading option descriptions from doc comments** (`systemone`). Charming, and it ties the API contract to rustdoc formatting; `options!` keeps the description next to the key where a reviewer looks for it.
- **The `secrecy` crate for the key.** judgment redacts `Debug` and never logs the key; zeroising memory guards against a threat this deployment does not have.

## What to do with this

Items 1 to 4 are one release, small, and each removes a class of failure that a second provider or a support ticket would expose; they are worth a beads epic now. Items 5 to 7 are the "parity" release that makes the rustdoc's comparison with the official SDK true. Items 8 to 12 wait for the consumer that needs them, with 9 and 10 the first to arrive if the self-hosting question in the research note is ever answered yes. This paragraph first said that nothing on the list changes a signature a consumer holds except the `Answer` variant in item 2, and that the variant was additive. Both halves were wrong: a new variant on an exhaustive public enum breaks every exhaustive `match` outside the crate ([Cargo's SemVer rules](https://doc.rust-lang.org/cargo/reference/semver.html#enum-variant-new)), and items 1, 3, 5 and 7 change error variants, public struct fields and a method's receiver as well. The release that did items 1 to 7 lists thirty-odd breaking changes in [its CHANGELOG](https://github.com/chussenot/signalman/blob/main/crates/judgment/CHANGELOG.md); from 0.2 on, `Error` and `Answer` are `#[non_exhaustive]`, so a new variant is additive for real.

## What shipped in judgment 0.2.0

Items 1 to 7 shipped together as judgment 0.2.0 (signalman 0.4.0 took it), in one epic, `signalman-7v9`, one bead per item. Items 8 to 12 still wait for their consumer. How each landed, and where it departs from the ranking above:

| Item | What shipped | Where it differs from the ranking |
|---|---|---|
| 1. Request id | `x-typesafe-request-id` on `Response::request_id`, on every error that came from an HTTP response (`Error::request_id()`, and a `[request_id …]` suffix on the message), and as the `request_id` field of the `typesafe.evaluate` and `typesafe.list_models` spans | Read in `client.rs`, not in the shared retry loop, which stays generic across the three upstreams and hands back the last response's headers in `http::Completed::headers`. It is the last attempt's id only, and optional everywhere, because the OpenAPI document lists no response headers; Laya sends none |
| 2. Tolerant decode | `Answer::Unknown(Value)` with a `warn` event naming the key and kind (escaped and cut to 64 characters); `Response::extra` keeps every undocumented top-level field, so Laya's `routing` or OpenRouter's `provider` can be logged; a missing `usage`, or null counts, read as zero | The known answer kinds stay strict, and `Answer` is now `#[non_exhaustive]` |
| 3. Verify | `Response::verify(&Questions)` checks every id, kind, Choice key and Score legend, and every backend in the crate runs it: `Client`, `Fake`, `Replay`, `Recorder`. A 2xx that does not fit is an error (`Error::is_unfit`), reported to the observer as `unfit` and never retried | A structured Score level may be echoed as itself or as its compact JSON. Laya echoes it as itself; the compact form has not been seen from any server, and the hosted API's echo is still to be observed. signalman no longer reads an off-list Choice option as the no-match option: the triage fails, the alert keeps no tags and no note, and `eval` records the case as failed ([Triage](../triage.md)) |
| 4. OpenAPI contract test | The vendored `api.typesafe.ai/openapi.json` (0.2.0) validates the requests the builders produce and the responses the `Fake` and the committed recordings hold (`crates/judgment/tests/contract.rs`); an ignored drift test compares the copy with the URL (`tests/openapi_drift.rs`); signalman validates its own TypeSafe traffic against the same document | As ranked |
| 5. Retry parity, stated | `retry-after-ms`, then `Retry-After` in seconds, then as an HTTP date, all under `retry_after_max`; one-sided jitter; an optional total `budget`; `RetryPolicy::conservative()` (408, 429 and failures before the request left the process); a parity table on `RetryPolicy` that lists what matches Python 0.7.1 and JS 0.6.0, what deliberately differs and what is not implemented | The budget is off by default, so no consumer's timing changed. `x-typesafe-retry-count` is reserved (a caller cannot set it) but not yet sent. A `Retry-After` of `inf` or 1e20 used to panic in the loop; it is now ignored. The client follows no redirect, like the Python SDK |
| 6. Per-call overrides | `Client::evaluate_with(&Request, &CallOptions)` with a per-call timeout, retry policy, headers and extra body fields, plus `ClientBuilder::default_header` | Not as fields on `Request`: `Request` is unchanged, so struct literals and signalman's `--print-request` keep the documented body. The model stays on `Request`, which is already per call, because a second override would make the span's `model` field and the `Recorder`'s hash name a model the call did not use |
| 7. Schema fixes | A 400 is `Error::InvalidRequest` like 422, with the body's issues parsed into `ValidationIssue`s; 403 is `Error::PermissionDenied`; `Error::InvalidApiKey` applies the Python SDK's key hygiene at `build()`; the `/v1/models` and question-limit notes are corrected | `instructions` may be null, but a null is still sent as `"instructions": null` rather than left out: the schema accepts it and Laya's server reads the key unconditionally. A Noul with neither instructions nor criteria is refused, since the id is never shown to the model |

The evidence, as of the release: the workspace tests (wiremock for the client, no network in the default run); the ten ignored live tests in `crates/judgment/tests/live.rs`, all passing against `laya-serve` ([judgment against Laya typed-decisions](../judgment-laya-typed-decisions.md)); the committed Laya recordings, which still replay to an accuracy of 0.725 on 200 questions under the stricter decoder; and signalman's committed Jev recordings (`examples/eval/runs/jev-1.13.0`), which replay to a decision agreement of 1.00. None of the 0.2 behaviour has been checked against a live TypeSafe account yet: the hosted API has answered this client once, under 0.1. The full list of changes, the breaking ones included, is in the crate's [CHANGELOG](https://github.com/chussenot/signalman/blob/main/crates/judgment/CHANGELOG.md).
