# rustsafe

A small HTTP API in Rust that pushes correctness into the type system. The
goal is that invalid states are **unrepresentable** and that the API contract
is **derived from the code**, so neither can drift.

Three techniques, each isolated so it can be lifted into another service:

| Technique | Where | What it buys |
|---|---|---|
| Parse, don't validate | `src/domain/user.rs`, `src/domain/money.rs` | A value of type `Email`, `Username` or `Money` is valid by construction. Deserialisation *is* validation (`#[serde(try_from)]`), so handlers never re-check. |
| Typestate lifecycle | `src/domain/order.rs` | `Order<Draft>`, `Order<Submitted>`, `Order<Paid>` are distinct types. Calling `pay()` on a draft is a **compile error** (proved by a `compile_fail` doctest). Runtime dispatch happens once, in the `AnyOrder` enum at the storage boundary. |
| Contract from types | `src/api/mod.rs`, `/openapi.json` | OpenAPI 3.1 generated by `utoipa` from the same structs the handlers deserialise. A handler cannot be routed without being documented (`routes!`). Schema bounds (`minimum: 0`, `minLength: 3`) match the constructors. |

Supporting pieces: one `ApiError` enum with a single `IntoResponse` that emits
RFC 9457 problem details, a `ValidJson<T>` extractor mapping malformed JSON to
400 and invariant violations to 422, distinct `UserId` / `OrderId` newtypes so
identifiers cannot be mixed up, and an in-memory store with an atomic
read-modify-write for lifecycle transitions.

## Run

```sh
cargo run
# RUSTSAFE_ADDR=0.0.0.0:9000 RUST_LOG=debug cargo run
```

```sh
curl -s -X POST localhost:8080/users -H 'content-type: application/json' \
  -d '{"username":"ada","email":"Ada@Example.org"}'
# {"id":"…","username":"ada","email":"ada@example.org"}

curl -s -X POST localhost:8080/users -H 'content-type: application/json' \
  -d '{"username":"bob","email":"nope"}'
# 422 {"title":"Unprocessable Entity","status":422,"detail":"invalid field: email: invalid email address: missing '@' …"}

curl -s -X POST localhost:8080/orders -H 'content-type: application/json' \
  -d '{"customer_id":"<user id>","total":1500}'
curl -s -X POST localhost:8080/orders/<order id>/pay
# 409 {"title":"Conflict","status":409,"detail":"order is draft, expected submitted"}
curl -s -X POST localhost:8080/orders/<order id>/submit
curl -s -X POST localhost:8080/orders/<order id>/pay
# 200 {…,"status":"paid","submitted_at":"…","paid_at":"…"}

curl -s localhost:8080/openapi.json | jq .paths
```

## Design notes

- **Why newtypes over a `validate()` step?** A validation function is a
  convention; a constructor is a guarantee. With `#[serde(try_from = "String")]`
  the only way to obtain an `Email` from the wire is through `Email::parse`, so
  there is no code path that forgets it.
- **Why typestate *and* an enum?** Typestate gives compile-time transition
  safety inside the domain. Stored data has a runtime state, so one closed enum
  (`AnyOrder`) is matched once per request; every arm hands back a concrete
  `Order<S>` and the compiler takes over again. Adding a state forces every
  `match` to be updated.
- **Why hand-written schemas for `Money` and `Username`?** `utoipa`'s derive
  cannot attach `minimum` / `minLength` to a newtype. Implementing
  `PartialSchema` by hand keeps the published bounds identical to the
  constructor's checks.
- **Errors carry structure, not strings.** `ApiError::InvalidTransition`
  holds `actual` and `expected` as `OrderStatus`, so the 409 body is built from
  data, not parsed from a message.
